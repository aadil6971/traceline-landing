      03 What it does

      Made for the 2 a.m. page.

      Logs tell you something broke. Traceline tells you where, in which service, on which line, and what changed. Five things it does that a pile of dashboards does not.

      1. 01

        One request, every hop

        Traceline carries a trace ID through HTTP, gRPC, Kafka, SQS and scheduled jobs. When a request changes process, language or queue, the trail stays whole. You see one request, not five log streams.

        • HTTP
        • gRPC
        • Kafka
        • SQS
        • Cron
      2. 02

        Lands on the line

        Every error links to the file, the line and the commit that put it there. Source is read at deploy time, so what you see is what ran. The person who last touched it is one click away.

        • Source preview
        • Git blame
        • Stack frames
      3. 03

        Queues and databases count too

        Time spent waiting in a queue is time your user waited. Traceline measures the gap between publish and consume, and flags N+1 queries without a single hand-written span.

        • Postgres
        • MySQL
        • Redis
        • RabbitMQ
      4. 04

        Keep every error. Sample the rest.

        Sampling happens after the request finishes, so we know how it ended. Every failed or slow trace is kept in full. Healthy traffic is sampled down. Your bill follows your problems, not your traffic.

        • Tail-based
        • Per-service rules
      5. 05

        Diff any two traces

        Put a slow request next to a healthy one. Traceline lines up the spans and shows the one that grew. No more scrolling two waterfalls and squinting.

        • Span alignment
        • Regression view
